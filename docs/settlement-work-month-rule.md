# 作業月を尊重する精算ルール

- 時間報酬は終了済み・未除外の稼働ログをJSTの月境界で分割し、実際の稼働月へ計上する。
- 固定報酬は最新の有効な完了報告月へ帰属する。支払対象の完了条件は **IssueがclosedかつStatusがDone**。関連PRの有無・状態は条件に含めない。
- 完了報告後に再稼働した場合は未確定の完了報告を失効させる。再報告した月へ固定報酬だけを移す。
- 同じ完了報告のIssue完了状態だけが変化した場合は再申請不要。報告やログの変更は再申請対象。
- 承認後に完了条件を満たした固定報酬は、元の完了報告月の追加支払いとなる。

## 時間報酬の上限

Issue全期間・全作業者の時間報酬を合算する。未申請月の終了済みログと承認済みのログ修正も含む。月次申請済みの時間単価を維持し、報酬方式も各月の精算と同じ完了報告スナップショットを使う。承認済みの月・作業者についてはログの再計算に代えて承認済み金額を一度だけ加算する。

上限超過時は、そのIssueに関係する対象月の月次申請と月次承認をブロックする。例えば上限1万円に対し8月6,000円・9月6,000円なら、どちらも未申請であっても超過として扱う。

## 承認済み情報と通知書

通常支払い通知書の再作成では承認済みの金額・明細・稼働ログを復元する。Issueの現在状態や追加支払いによって通常支払いを再計算しない。宛先と予定日は再作成時点の登録内容を使い、過去の通知書は上書きしない。

精算スナップショットのJSON形式v4では、比較対象のハッシュに加えて復元用原本全体のハッシュを保存する。合計が同じでも、稼働分数・日時・Issue・件名・URLが壊れていれば復元しない。jsonbのキー並べ替えと日時のJSON変換は許容する。

既存v3は原本の比較対象項目と保存済みハッシュを照合し、v2は旧キーを考慮してハッシュを検証する。ハッシュがない旧形式については構造と金額整合を検証する。件名が保存されていない旧明細はIssue番号と「保存時の件名なし」を表示し、現在の件名から過去の事実を補わない。旧形式でハッシュ対象外だった情報の破損は遡って検証できない。既存スナップショットは書き換えない。

## 初回単価の永続保存

`issue_hourly_rates` にIssue＋作業者の単価、最初の帰属月、保存日時・保存者・由来を記録する。月次申請・単価・監査・通知用データを同じトランザクションで保存し、再申請からIssueを外しても単価は削除・更新しない。

V2の最初の成功申請時に、現存する旧申請・承認スナップショットからも保存日時順で単価を継承する。同時刻・同月なら承認記録を優先する。差し替え直前の旧申請も読み取るため、最初のV2再申請で明細を外しても単価を失わない。承認済み・支払い済み月の内容は変更しない。過去に既に失われた記録からの単価復元はできない。

## 申請・承認の競合検知

V2は計算前のDB入力の版を取得し、保存トランザクション内で再照合する。ログ・修正申請・完了報告・他月の精算や単価が変わった場合は保存せず、再読み込みを求める。失敗した操作では監査・通知・通知書・新しい単価も保存しない。

現行規模では計算入力8表の短い表ロックを使用する。既存の書き込み経路やINSERTも保護するためで、GitHub取得やメール準備はロックの外で行う。ロック待機は5秒、保存statementは10秒を上限とする。無関係な作業者の更新でも安全側に再読み込みが必要になる場合がある。規模拡大時はIssue単位の版管理へ移行する。ロック取得後に別statementで照合する設計は[PostgreSQLの整合性検証の指針](https://www.postgresql.org/docs/17/applevel-consistency.html)に従う。

### リリース

`0011_tan_lenny_balinger.sql` は単価テーブル追加のみ。V2無効時の通常操作は新テーブルを参照しないため、無効状態でデプロイ→CI migration確認→V2有効化の順を維持する。本番のデータ移行・フラグ変更は別途確認してから行う。

## GitHub取得失敗

新しい完了確認・申請・承認を行わず、エラーを表示する。通常支払い欄は承認時点の保存結果を優先し、未承認なら申請時点の結果を表示する。表示元と最新状態を確認できない旨を明示する。保存結果がない、または破損している場合は金額を「確認できません」とし、0円や変更なしとして扱わない。

承認済みスナップショットからの通知書再作成はGitHubに依存しない。保存内容の破損や金額不整合があれば再作成を拒否する。
