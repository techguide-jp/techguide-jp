# 作業月を尊重する精算ルール

- 時間報酬は終了済み・未除外の稼働ログをJSTの月境界で分割し、実際の稼働月へ計上する。
- 固定報酬は最新の有効な完了報告月へ帰属する。支払対象の完了条件は **IssueがclosedかつStatusがDone**。関連PRの有無・状態は条件に含めない。
- 完了報告後に再稼働した場合は未確定の完了報告を失効させる。再報告した月へ固定報酬だけを移す。
- 同じ完了報告のIssue完了状態だけが変化した場合は再申請不要。報告やログの変更は再申請対象。
- 承認後に完了条件を満たした固定報酬は、元の完了報告月の追加支払いとなる。

## 時間報酬の上限

Issue全期間・全作業者の時間報酬を合算する。未申請月の終了済みログと承認済みのログ修正も含む。月次申請済みの時間単価を維持し、報酬方式も各月の精算と同じ完了報告スナップショットを使う。承認済みの月・作業者についてはログの再計算に代えて承認済み金額を一度だけ加算する。

上限超過時は、そのIssueに関係する対象月の月次申請と月次承認をブロックする。例えば上限1万円に対し8月6,000円・9月6,000円なら、どちらも未申請であっても超過として扱う。

## 承認済み情報と通知書

通常支払い通知書の再作成では承認済みの金額・明細・稼働ログを復元する。Issueの現在状態や追加支払いによって通常支払いを再計算しない。宛先と予定日は再作成時点の登録内容を使い、過去の通知書は上書きしない。

精算スナップショットのJSON形式v3では復元用の元明細も保存する。既存v2と旧形式も読み取る。件名が保存されていない旧明細はIssue番号と「保存時の件名なし」を表示し、現在の件名から過去の事実を補わない。既存レコードの書き換えとDBスキーマ変更は行わない。

## GitHub取得失敗

新しい完了確認・申請・承認を行わず、エラーを表示する。通常支払い欄は承認時点の保存結果を優先し、未承認なら申請時点の結果を表示する。表示元と最新状態を確認できない旨を明示する。保存結果がない、または破損している場合は金額を「確認できません」とし、0円や変更なしとして扱わない。

承認済みスナップショットからの通知書再作成はGitHubに依存しない。保存内容の破損や金額不整合があれば再作成を拒否する。
