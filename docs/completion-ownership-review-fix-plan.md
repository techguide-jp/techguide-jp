# 完了報告のIssue単位の重複防止

## 対象

PR #35の担当変更後の固定報酬二重計上を修正する。IssueのclosedかつDoneという完了条件、時間報酬の作業者・稼働月への帰属は変更しない。

## 判定

- 未確定の有効報告はIssue全期間・全作業者から最新1件を選ぶ。同時刻は登録日時、IDで順序を固定する。
- 完了確認済みが1件あれば、その報告を維持する。担当変更だけでは固定報酬の帰属を変えない。
- 完了確認済みが複数ある既存不整合は自動取消・再配分せず、新規対象化・月次申請・承認を止めて管理者の確認を求める。
- 新報告は古い未確定報告を作業者横断で失効させ、履歴・監査を残す。確認済み・固定報酬計上済みのIssueの差し替えや、より古い完了日時による置き換えは拒否する。
- 通常精算は月抽出前にIssue単位で選択する。追加支払いもDBの最新状態で選び直す。既存の通常承認・追加支払い・支払い通知書は書き換えない。

## 実装

既存の精算入力ロックとRead Committedトランザクションを再利用する。ロック取得後の別statementで再検証し、報告提出・完了確認・月次承認の競合を直列化する。選択規則は純粋関数、永続化はRepositoryへ分離する。外部APIはロック内で呼ばない。DBスキーマ変更や既存データの一括移行は行わない。

## 検証・反映

担当変更、月またぎ、取り下げ済み報告、確認済み報告の保護、通常／追加支払い、並行提出／確認、待機中の変更、監査と既存支払い記録の不変を単体・実PostgreSQLで検証する。既存のformat:check、check、lint、test、test:db、e2e、buildを実行し、#35へpushして再レビューを依頼する。マージ・本番更新・#36・Wiki公開は行わない。
