# 依頼者直接発注・受諾・精算フロー設計

## 1. 文書情報

- ステータス: 実装前の確定設計
- 対象システム: `techguide-jp` 稼働精算サイト
- 対象GitHub Project: `techguide-jp/projects/7`（techguide-jp 外注管理）
- 設計書URL: https://github.com/techguide-jp/techguide-jp/blob/main/docs/direct-contract-order-flow-design.md
- 契約モデル: 依頼者と委託エンジニアの直接契約

本書は、現在のTechGuide内部発注フローを維持したまま、依頼者が自社リポジトリのIssueを発注書として委託エンジニアへ直接発注できるフローを追加するための確定設計である。

## 2. 目的と対象外

### 2.1 目的

- `依頼者 → TechGuideシステム → 委託エンジニア` の案件管理を可能にする。
- 契約と報酬支払いは `依頼者 → 委託エンジニア` の直接取引とする。
- 依頼者がGitHubで直接作成したIssueを発注書として扱う。
- リポジトリ固有の技術情報や基本条件は、Issueごとに再入力させず、版付きリポジトリプロフィールから継承する。
- Issue作成後にTechGuide運営のレビューを挟み、レビュー済みの候補案件だけをエンジニアの受諾待ち一覧へ出す。
- 依頼者の月次承認と同時に、依頼者名義の支払通知書をシステムが自動生成する。
- TechGuideは依頼者へシステム利用料を請求する。

### 2.2 今回の実装計画で対象外とするもの

- TechGuideによる報酬の収納代行、立替払い、送金代行
- 雇用契約のあっせん、エンジニアへの指揮命令、勤務場所・勤務時間の拘束
- GitHub上の全機能の再実装
- Pull Requestレビュー機能
- GitHubリポジトリへのIssue Form自動コミット
- 公開リポジトリでの直接契約案件
- 銀行API、決済代行サービス、マイナンバー管理
- 適格請求書発行事業者番号の外部API自動照合
- 法律・税務専門家への自動相談または適法性の保証

## 3. 役割と契約関係

| 役割              | 責任                                                                                            |
| ----------------- | ----------------------------------------------------------------------------------------------- |
| 依頼者            | Issue作成、リポジトリ条件の確認、報酬・納期・検収条件の提示、月次稼働承認、エンジニアへの支払い |
| TechGuideシステム | GitHub連携、条件の版管理、運営レビュー支援、受諾記録、稼働・精算管理、帳票生成、監査ログ        |
| TechGuide運営     | 依頼内容のレビュー、候補者選定、法務・運用上の不備確認、例外対応                                |
| 委託エンジニア    | 条件確認、受諾または辞退、作業、月次確定申請、支払通知書の確認または訂正依頼                    |

- 業務委託契約の当事者は依頼者と委託エンジニアとする。
- TechGuideは契約・支払いの記録と運用を支援するが、業務委託料の支払者にはならない。
- TechGuideと依頼者の間には、別途システム利用契約が成立する。
- TechGuide利用料は、依頼者が承認した業務委託報酬を基礎としてTechGuideから依頼者へ請求する。

| 情報                               | 正本                                 | 更新単位                       |
| ---------------------------------- | ------------------------------------ | ------------------------------ |
| 依頼者の法的情報・請求先・利用料率 | 依頼者組織プロフィール               | 組織・有効期間単位             |
| 技術構成・必須スキル・開発ルール   | リポジトリプロフィール               | リポジトリ・版単位             |
| 業務内容・成果物・納期・報酬       | 依頼者が作成したGitHub Issue         | Issue単位                      |
| Status・報酬計算用項目             | techguide-jp 外注管理Project         | Issueから同期した正規化表示    |
| 運営レビュー時点の発注条件         | Issueレビュースナップショット        | レビュー版単位                 |
| 契約成立条件                       | 受諾スナップショット                 | 受諾単位                       |
| 稼働・支払額                       | 依頼者別月次精算スナップショット     | 依頼者組織・月・エンジニア単位 |

報酬条件の入力元はIssueとする。外注管理Projectの報酬項目はIssueからシステムが同期し、一覧、計算、ヘルスチェックに使用する。IssueとProjectを別々に人手で編集して同格の正本にはしない。

## 5. 認証と権限

### 5.1 認証

- TechGuide運営と委託エンジニアは既存のGitHub OAuthを使用する。
- 依頼者はTechGuideから送られる有効期限24時間の一度だけ使える招待リンクで組織へ参加する。
- 依頼者の継続ログインは招待先の確認済みメールアドレスへ送るワンタイムリンクを使用する。
- GitHubでIssueを作成する依頼者は、ポータル上でGitHubアカウントを一度連携する。
- GitHub WebhookのIssue作成者が、有効な依頼者組織メンバーへ紐づかなければレビューをブロックする。

### 5.2 ロール

| 操作                       |  TechGuide管理者 | 依頼者組織管理者 | 依頼者承認者 | 候補エンジニア | 受諾エンジニア |
| -------------------------- | ---------------: | ---------------: | -----------: | -------------: | -------------: |
| 依頼者組織・メンバー管理   |                ○ |       自組織のみ |            × |              × |              × |
| リポジトリプロフィール編集 |                ○ |       自組織のみ |   自組織のみ |              × |              × |
| リポジトリプロフィール確定 | 依頼者再確認必須 |                ○ |            ○ |              × |              × |
| 運営レビュー               |                ○ |                × |            × |              × |              × |
| 候補者選定                 |                ○ |                × |            × |              × |              × |
| 受諾・辞退                 |                × |                × |            × |       自分のみ |       自分のみ |
| 月次確定申請               |                × |                × |            × |              × |       自分のみ |
| 月次承認・通知書発行       |   閲覧・例外対応 |     設定により可 |            ○ |              × |              × |
| 通知書確認・訂正依頼       |   閲覧・例外対応 |             閲覧 |         閲覧 |              × |       自分のみ |
| 振込済み登録               |   閲覧・例外対応 |     設定により可 |            ○ |              × |              × |

`ADMIN_GITHUB_LOGINS` は初期管理者のブートストラップと緊急時のフォールバックに限定し、複数管理者の恒久的なロールはDBで管理する。

## 6. GitHub Appとリポジトリ登録

### 6.1 GitHub App権限

- Repository Metadata: read
- Repository Contents: read
- Repository Issues: write
- Webhook: `installation`, `installation_repositories`, `issues`

Contents writeとAdministration権限は付与しない。依頼者リポジトリへのAPIアクセスはinstallation tokenを使用する。TechGuide所有のProject #7は既存のProject用認証アダプターを使用し、依頼者リポジトリ用のinstallation tokenと責務を分ける。

### 6.2 登録フロー

1. 依頼者組織管理者がGitHub Appを選択した非公開リポジトリへインストールする。
2. `installation` または `installation_repositories` Webhookを受信する。
3. GitHub repository ID、installation ID、owner/name、可視性、デフォルトブランチを依頼者組織へ紐づける。
4. Languages、Topics、README、主要manifestを取得する。
5. システムが決定的に抽出できる情報をプロフィール下書きへ設定する。
6. 依頼者が不足情報を補い、内容を確認して初版を有効化する。

READMEやmanifestの全文は永続化せず、確認済みの構造化情報、参照URL、取得元commit SHA、取得日時だけを保存する。秘密情報を抽出・保存しない。

### 6.3 リポジトリ状態

- `profile_required`: App連携済み、プロフィール未確定
- `active`: App連携と有効プロフィールあり
- `access_suspended`: App停止、削除、権限不足
- `archived`: 新規発注を受け付けない

`active` 以外のリポジトリからIssueを受信しても記録は残すが、候補者への公開と運営レビュー完了をブロックする。

## 7. リポジトリプロフィール

### 7.1 登録項目

- システム概要、目的、対象ユーザー、対象範囲、対象外
- 必須スキル、歓迎スキル、必要経験
- 言語、フレームワーク、ランタイム、パッケージマネージャー
- DB、インフラ、外部サービス
- セットアップ、開発、テスト、lint、buildコマンド
- ブランチ、PR、レビュー、コミットルール
- 完了条件、デプロイ・リリース担当範囲
- 環境変数、権限、秘密情報の受渡方法
- 連絡方法、応答期待、禁止事項、変更対象外
- 参照ドキュメントURL、自由記述

報酬、納期、個別成果物、個別検収条件、経費、支払期日、源泉徴収区分はリポジトリプロフィールへ含めず、Issue単位で設定する。

### 7.2 版管理

- 状態は `draft`, `active`, `superseded` とする。
- リポジトリごとに単調増加する版番号を持つ。
- 有効版は同時に1件だけとする。
- 内容、確認者、確認日時、取得元commit SHA、内容ハッシュを保存する。
- TechGuide管理者が修正した場合も、依頼者による再確認後に有効化する。
- Issueレビュー時に有効版を固定する。
- 受諾前に有効版が変わった場合はレビューを無効化し、再レビューする。
- 受諾後の更新は成立済み案件へ遡及せず、次回以降のIssueへ適用する。

## 8. Issueを発注書とするフロー

### 8.1 Issue作成

- 依頼者は自社リポジトリで標準Issue Formを使用してIssueを直接作成する。
- Issue Formは依頼者が自社リポジトリへ配置する。GitHub Appはファイルを書き込まない。
- v1は非公開リポジトリのみ対応する。
- Issue Formには、運営レビュー時に固定されたリポジトリプロフィール版を本Issueの条件へ組み込む旨を明記する。

必須入力:

- 業務内容と目的
- 成果物
- 検収条件
- 納期
- 報酬方式
- 固定報酬額（円・税抜）
- 追加精算上限（円・税抜）
- 時間単価（円・税抜）
- 経費負担と上限
- 支払期日または支払期日ルール
- 源泉徴収区分
- 個別の変更・中止条件
- Issue Form版

### 8.2 Project同期

既存の必須項目を維持する。

- `Status`
- `報酬方式`
- `固定報酬額（円・税抜）`
- `追加精算上限（円・税抜）`
- `時間単価（円・税抜）`

追加するProject項目:

- `依頼区分`: `TechGuide発注` / `依頼者直接発注`
- `発注ID`
- `依頼者組織`
- `リポジトリプロフィール版`

追加するStatus選択肢:

- `Review`
- `Awaiting Acceptance`

候補者一覧、法的情報、プロフィール全文、監査情報はProjectへ保存しない。

### 8.3 状態遷移

| 発注状態              | Project Status        | 説明                                       |
| --------------------- | --------------------- | ------------------------------------------ |
| `review_pending`      | `Review`              | Issue取込済み、運営確認待ち                |
| `awaiting_acceptance` | `Awaiting Acceptance` | レビュー済み、候補者受諾待ち               |
| `accepted`            | `Todo`                | 受諾済み、リポジトリアクセス準備待ちを含む |
| `in_progress`         | `In Progress`         | 稼働開始済み                               |
| `completed`           | `Done`                | 作業完了                                   |
| `all_declined`        | `Reject`              | 全候補者辞退、再選定待ち                   |
| `change_pending`      | `Review`              | 条件変更により再レビュー待ち               |
| `cancelled`           | `Reject`              | 取消済み                                   |

## 9. 運営レビュー

レビュー時に次を検証する。

- Issue作成者が有効な依頼者組織メンバーであること
- GitHub Appが対象リポジトリへアクセスできること
- リポジトリプロフィールに有効版があること
- Issue Form版と必須項目が有効であること
- Issue報酬値とProject報酬項目が一致すること
- 支払期日が既定ルールと原則60日以内の条件を満たすこと
- 経費、源泉徴収、検収、変更・中止条件が明示されていること
- 候補者が1名以上選定されていること

レビュー承認時に次を一つのスナップショットとして保存する。

- GitHub repository ID、Issue ID、Issue番号、作成者、タイトル、本文、更新日時
- Issue本文ハッシュとIssue Form版
- Project item IDと報酬項目
- 依頼者組織・法的情報
- リポジトリプロフィール版・内容ハッシュ
- 支払条件・源泉徴収区分
- 標準約款版
- レビュー者・レビュー日時

レビュー完了後、GitHub Issueへプロフィール版、スナップショット識別子、確認用URLを含むbotコメントを一度だけ投稿する。

Issue本文または報酬項目が受諾前に変わった場合はレビューを無効化する。受諾後の変更は既存条件を上書きせず、変更版として再レビュー・再受諾する。

## 10. 候補者選定と受諾

### 10.1 スキル絞り込み

- 既存の作業者プロフィール `skills` と、リポジトリプロフィールの必須・歓迎スキルを比較する。
- 大文字小文字、前後空白、既知の別名を正規化する。
- 必須スキル一致数の多い順を既定表示とする。
- 管理者には一致した必須スキル、不足・未登録の必須スキル、一致した歓迎スキルを表示する。
- 不一致を理由に自動除外しない。運営は理由を確認して候補者を追加できる。

### 10.2 受諾待ち一覧

- 運営が指定した候補者だけが対象案件を閲覧できる。
- 他候補者の氏名、人数、受諾・辞退状況は表示しない。
- 非公開GitHubリポジトリへ未招待でも、ポータル上でレビュー済みのIssue本文とリポジトリプロフィールを閲覧できる。
- コード、README全文、manifest全文、秘密情報は候補者へ開示しない。

表示を次のセクションへ分ける。

1. Issue固有情報
2. リポジトリ固有情報と参照版
3. 報酬・経費・支払条件
4. 運営レビュー情報
5. 受諾・辞退操作

### 10.3 受諾

- 受諾直前にIssue・Project・プロフィール版のハッシュを再検証する。
- 一つの発注に有効な受諾は1件だけとし、DBの一意制約とトランザクションで先着一名を確定する。
- 受諾者をGitHub assigneeへ設定し、Project Statusを `Todo` にする。
- 辞退は候補者単位で記録し、他候補者の受諾機会を維持する。
- 全候補者が辞退した場合は `all_declined` として運営へ戻す。
- 依頼者が受諾者へGitHubアクセスを付与し、アクセス準備完了後に稼働開始を許可する。
- 未レビュー、未受諾、別ユーザー、アクセス未準備のIssueは、画面と直接POSTの両方で稼働開始を拒否する。

## 11. 月次精算と支払通知書

### 11.1 精算単位

直接契約案件は `依頼者組織 × 対象月 × エンジニア` ごとに精算する。別の依頼者組織のIssueを同じ申請、スナップショット、支払通知書へ混在させない。

### 11.2 月次確定フロー

1. エンジニアが依頼者ごとの月次稼働を確定申請する。
2. 依頼者承認者がIssue、成果物、稼働時間、報酬、経費、税、源泉徴収、支払期日を確認する。
3. 同じ画面で依頼者名義の支払通知書プレビューを確認する。
4. `稼働・支払額・支払通知書の内容を確認し、発行を承認する` を一度だけ実行する。
5. 一つのDBトランザクションで月次精算スナップショット、支払予定日、支払通知書、利用料計算基礎を保存する。
6. エンジニアへ支払通知書の確認を依頼する。
7. エンジニアは `確認済み` または `訂正依頼` を選択する。
8. 依頼者が銀行振込を実行し、システムへ振込日を記録する。

現行の「月次承認時に精算スナップショットと通知書を同一トランザクションでappendする」構造を再利用する。直接契約案件では承認者と支払者をTechGuide管理者から依頼者組織へ切り替える。

### 11.3 通知書

帳票名は `支払通知書（仕入明細書）` とし、生成処理はTechGuideシステム、書類の作成者・支払者は依頼者とする。

記載事項:

- 通知書番号、対象期間、発行日
- 作成者である依頼者の名称
- エンジニアの名称と、登録済みの場合は適格請求書発行事業者登録番号
- Issue別の役務内容
- 税率別の税抜額または税込額、適用税率、消費税額
- 経費
- 源泉徴収額
- 振込予定額
- 支払期日
- 依頼者承認者・承認日時

通知書状態:

- `preview`
- `issued`
- `confirmed`
- `correction_requested`
- `superseded`

依頼者・エンジニアの名称、税区分、役務内容、対象期間、税率別金額が不足している場合は月次承認をブロックする。振込先未登録は帳票発行を妨げないが、支払予定・支払済み登録をブロックする。

訂正時は旧通知書を上書きせず、新版をappendする。現在の承認スナップショットと一致する通知書だけを通常表示する。支払済み後の訂正は既存帳票を書き換えず、差額調整として別記録を作る。

エンジニアの確認待ちでも支払期日到来時の銀行振込をブロックしない。未確認を警告し、支払遅延を起こさない。

### 11.4 支払期日

- 既定は翌月14日とする。
- 依頼者承認時に変更できる。
- 給付を受領した日から原則60日以内となるよう検証する。
- 期日超過見込みと期日超過は運用ヘルスと通知対象にする。

## 12. TechGuide利用料

- 依頼者組織ごとに有効期間付きの利用料率を設定する。
- 発注受諾時点の料率版を発注へ固定する。
- 計算基礎は依頼者が承認した税抜業務委託報酬とする。
- 立替経費、消費税、源泉徴収による控除額は計算基礎へ含めない。
- 依頼者組織・対象月ごとに対象発注を集約し、TechGuideから依頼者へ請求書を発行する。
- 月次承認後の訂正は、元請求書を破壊せず調整行または次回請求で処理する。
- 利用料請求とエンジニアへの直接支払いは別の状態として管理する。

## 14. 画面とHTTP境界

### 14.1 依頼者向け

- `/requester/repositories`: GitHub App接続状態とリポジトリ一覧
- `/requester/repositories/[repositoryId]`: プロフィール編集・確認・版履歴
- `/requester/settlements`: 自組織の月次承認一覧
- `/requester/settlements/[month]/[worker]`: 稼働・通知書プレビュー・一括承認
- `/requester/invoices`: TechGuide利用料請求書

### 14.2 TechGuide管理者向け

- `/admin/issue-reviews`: レビュー待ち一覧
- `/admin/issue-reviews/[orderId]`: 条件検証、プロフィール版、候補者選定
- `/admin/requesters`: 依頼者組織とGitHub連携状態
- `/admin/direct-contract-health`: Webhook、App、Project、通知、期日の運用ヘルス

### 14.3 エンジニア向け

- `/offers`: 受諾待ち一覧
- `/offers/[orderId]`: Issue・リポジトリ条件・報酬の統合表示と受諾・辞退
- 既存 `/work`: 受諾済み案件の稼働開始・終了
- 依頼者別月次精算・通知書確認画面

### 14.4 Programmatic endpoint

- GitHub Webhookは `+server.ts` で署名検証、イベント識別、入力変換だけを行う。
- ページ操作は原則 `+page.server.ts` のform actionを使用する。
- routeは認証、入力検証、service呼出し、レスポンス変換に限定する。
- GitHub API、Project API、メール、帳票はserver adapterへ隔離する。
- 契約、レビュー、受諾、月次承認はserviceがトランザクション境界を持つ。

## 15. 通知、監査、運用ヘルス

### 15.1 通知イベント

- リポジトリプロフィール確認依頼
- Issue取込失敗、レビュー差戻し、レビュー完了
- 候補案件提示、辞退、受諾
- リポジトリアクセス準備依頼
- 月次確定申請、依頼者承認、通知書確認依頼、訂正依頼
- 支払期限接近、支払期限超過、振込済み
- TechGuide利用料請求

実送信基盤は既存Issue #22を使用する。業務操作のcommit後に配送し、通知失敗を理由に成立済み操作をrollbackしない。DBの配送記録と冪等キーで二重送信を防ぎ、送信結果不明を無条件に再送しない。

### 15.2 監査ログ

少なくとも次を記録する。

- actor、actor role、依頼者組織
- action、target type、target ID
- 前後の版・状態
- 条件ハッシュ
- 発生日時
- GitHub delivery IDまたは業務操作ID
- 成功、拒否、外部同期失敗

報酬、税、源泉徴収の確定値はスナップショットへ保存する。銀行口座番号、秘密鍵、OAuth token、メール本文全文を監査ログへ含めない。

### 15.3 運用ヘルス

- GitHub App installationの有効性と選択リポジトリ
- 必要権限とWebhook最終受信日時
- Project #7必須項目とStatus選択肢
- ProjectからIssue contentを取得できない状態
- Project同期・assignee同期の未解決エラー
- メール設定・配送失敗・結果不明
- 支払期日と通知書確認の滞留

取得不能を0件や正常として扱わず、`unavailable` または `partial` として表示する。

## 16. セキュリティとプライバシー

- 依頼者組織IDをすべての直接契約データへ持たせ、server側でtenant境界を検証する。
- 候補案件は指定候補者だけに返し、UI非表示だけに依存しない。
- 受諾操作、月次承認、通知書確認は直接POSTの権限回帰テストを持つ。
- Webhook署名、delivery IDの重複、イベント再送を検証する。
- installation token、OAuth token、暗号鍵、銀行情報をログへ出さない。
- 依頼者が閲覧できる振込先情報を、その依頼者と契約中のエンジニアへ限定する。
- 候補者へコードやリポジトリ内容を開示せず、レビュー済み発注条件だけを表示する。
- 通知書・請求書の個人情報は暗号化し、承認時点の値を凍結する。
- 外部URLは許可された `https:` リンクだけを表示し、安全な別タブ属性を付ける。

## 17. 法務・税務上の設計条件

- 利用規約、Issue Form、受諾画面に、契約当事者が依頼者とエンジニアであることを明記する。
- TechGuideが雇用契約のあっせん、指揮命令、勤怠拘束を行わないことを利用規約と運用手順へ明記する。
- フリーランス法の取引条件明示、支払期日、継続契約時の禁止事項・解除予告をレビュー項目へ含める。
- 支払通知書を仕入明細書等として扱う場合は、エンジニアによる内容確認記録を保存する。
- 適格請求書として扱う場合は登録番号と法定記載事項を検証する。
- 源泉徴収は受取人が個人かどうかだけで自動判定せず、報酬内容と受取人区分を確認する。
- リリース前に社内法務レビューを必須とする。弁護士・税理士確認はシステム上の必須ゲートにはしないが、判断困難な報酬区分や契約形態は専門家確認へエスカレーションする。

## 18. 移行と既存互換

- 既存のTechGuide発注案件を `TechGuide発注` として維持する。
- 既存の `/work`、稼働ログ、月次精算、支払い状態、通知書を破壊しない。
- 直接契約案件だけを新しい受諾・tenant・依頼者承認ガードの対象にする。
- 既存Issueを自動的に直接契約へ変換しない。
- 既存Project itemへ不足項目を一括書込みしない。
- schema変更は後方互換な追加から始め、旧ルートが新テーブルを必須としない順序で展開する。
- GitHub App、Project項目、メール、利用規約の準備が完了するまでfeature flagで直接契約の新規取込を無効にする。
- 各子Issue単独の完了では本番利用を開始しない。Epicの受入条件と運用確認を満たした時点で有効化する。

## 19. テスト方針

### 19.1 Unit

- Issue Formのparse・正規化・必須項目
- リポジトリプロフィール版とハッシュ
- 報酬項目同期と不一致検出
- スキル正規化と一致・不足表示
- 状態遷移、支払期日、利用料計算
- 支払通知書本文と訂正版

### 19.2 DB integration

- tenant境界
- リポジトリごとの有効プロフィール版一意制約
- 一つの発注に有効な受諾が1件だけであること
- 依頼者・月・エンジニア単位の精算分離
- 月次承認、通知書、利用料計算基礎の原子的保存
- 現在の承認と一致する通知書だけを通常表示すること
- append-only履歴と監査ログ

### 19.3 Webhook

- 正しい署名、誤った署名、署名対象payloadの改変
- delivery ID再送の冪等性
- App削除、repository追加・削除、Issue作成・編集
- GitHub API権限不足、rate limit、content不可視

### 19.4 E2E

- 依頼者招待からリポジトリプロフィール確定
- Issue作成、運営レビュー、候補者表示、受諾
- 非候補者と他組織による閲覧・直接POST拒否
- レビュー後変更による再レビュー
- 未受諾・アクセス未準備の稼働開始拒否
- エンジニア申請、依頼者一括承認、通知書確認・訂正
- 依頼者間で精算・通知書が混在しないこと
- 既存TechGuide発注フローの回帰

## 20. Epic完了条件

- 依頼者が非公開リポジトリを登録し、版付き基本条件を確定できる。
- 依頼者が作成したIssueが発注書として検証・レビューされる。
- 指定候補者だけがIssue固有情報とリポジトリ固有情報を確認できる。
- 最初の受諾者だけが契約者として確定する。
- 未受諾案件を稼働開始できない。
- 依頼者別に月次精算し、一つの操作で稼働・金額・通知書を承認できる。
- システム生成の依頼者名義通知書について、エンジニアの確認記録を保存できる。
- TechGuide利用料を依頼者組織別の契約料率で計算・請求できる。
- tenant境界、監査、通知、運用ヘルス、法務文書が整備される。
- 既存TechGuide発注フローが継続して動作する。

## 22. 確定した既定値

- Issue作成場所: 依頼者所有のGitHubリポジトリ
- Issue作成者: 依頼者本人
- リポジトリ: v1は非公開のみ
- リポジトリプロフィール登録: GitHub自動取得後に依頼者が確認
- プロフィール更新: 版管理し、受諾後は遡及しない
- 報酬入力: Issueへ依頼者が記載し、Projectへ自動同期
- 候補者: 運営が1名以上選定
- 受諾: 最初の受諾者が成立
- スキル: 表示と候補絞り込みに使用し、自動除外しない
- 月次承認: 稼働・金額・通知書を依頼者が一つの操作で承認
- 支払通知書: 依頼者名義でシステムが自動生成
- エンジニア確認: 明示確認または訂正依頼を記録
- 支払期日: 翌月14日を既定とし、原則60日以内
- 金銭移動: システム外の銀行振込
- 利用料基礎: 税抜業務委託報酬、経費・税・源泉徴収控除は除外
- 法務ゲート: リリース前の社内法務レビュー
