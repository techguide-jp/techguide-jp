# 案件URLで依頼する運用

既存メンバー向けに、GitHub Issue一件を一つの依頼単位として扱う。

1. Issue本文へ目的、作業範囲、成果物、完了条件、期限、参考資料を記載する。
2. 外注管理Projectへ追加し、担当者、Status、報酬条件を設定する。
3. 管理者の稼働管理画面で「依頼文＋URLをコピー」を押し、チャットで送る。
4. 担当者は案件詳細で内容を確認し、チャットで受領を返信する。実際の作業開始時に稼働を開始する。
5. 成果物をIssueまたはPRへ提出し、稼働終了、完了報告、既存の月次精算へ進む。

依頼内容の正本はIssue、報酬の正本はProject、稼働・完了報告・精算は既存DB。新しい受諾状態や契約情報は追加しない。

## 実装範囲

- `/work/{owner}/{repo}/{number}` で案件詳細、報酬、本人の稼働履歴を表示する。
- 一覧から詳細へ移動でき、管理画面・詳細画面から依頼文とURLをコピーできる。
- GitHub OAuth後に元の案件へ戻る。戻り先は案件詳細の内部URLのみ許可する。
- 担当者本人と管理者だけが閲覧できる。本文の取得前にProjectの担当を確認する。
- 開始・終了・完了報告は既存の業務処理を呼び、担当者本人だけ操作できる。
- 本文は見出し、箇条書き、タスクリスト、コード、基本的なリンク・強調を安全に表示する。チェック状態はIssue本文から表示し、変更はGitHubで行う。表などの詳細はGitHubでも確認できる。
- GitHub取得失敗は不存在や未設定と混同せず、エラーと代替リンクを表示する。
- コピー失敗時は手動コピー用の文面を表示する。

既存Project用トークンのIssue読み取り権限を使用し、OAuthスコープ・DBスキーマ・報酬計算を変更しない。本文やラベルは既存精算スナップショットへ保存しない。

## 検証

権限外閲覧、担当外の直接POST、別案件の終了指定、外部へのログイン転送、OAuth state不一致、API失敗を単体テストで確認する。専用ローカルテストDBで案件詳細、一覧導線、コピー、開始・終了、完了報告をE2E確認し、PCとスマートフォンの画面を確認する。
