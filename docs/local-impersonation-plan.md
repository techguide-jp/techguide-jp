# ローカルでのユーザー切り替え

## 目的と利用方法

実際に対象者のGitHubでログインせず、ログイン済みの管理者が登録ユーザーの画面と申請・編集をローカルで確認できるようにする。管理者ナビゲーションの「ユーザー切替」から対象者を選び、全画面のバナーで擬似ログイン中のユーザーを確認し、管理者へ戻れる。

## 認証と操作範囲

- 開発サーバー、localhost / 127.0.0.1 / IPv6ループバック、ローカルDB、メールpreviewモードをすべて満たす場合だけ有効にする。Vercel上、本番ビルド、リモートDBでは画面と直接POSTの両方を拒否する。
- 元の管理者セッションを保持し、毎リクエストで有効な管理者であることを確認する。擬似ログイン用Cookieは元のセッションに署名で結び付け、有効期間を1時間とする。対象者の実セッションやログイン履歴は作成しない。
- 対象者はローカルDBの登録ユーザーから選択する。対象者の権限で既存画面・本人限定の申請や編集を実行し、元の管理者権限を引き継がない。開始・終了はPOSTで行い、元の管理者と対象者を監査ログに残す。
- 開発サーバーではフレームワーク標準のCSRF Origin検査が省略されるため、開始・終了と擬似ログイン中の更新リクエストに同一Originの検査を追加する。
- 操作結果はローカルDBに保存される。メールは既存のプレビュー配送を使用し、GitHub Projectの外部更新は擬似ログイン中のリクエストだけ停止する。稼働開始はローカルに記録し、外部同期の成功扱いや再試行キューへの追加はしない。
- リクエストごとのコンテキストで外部更新を制御し、並行している別ユーザーの処理へ設定を漏らさない。無効なCookie付きの更新リクエストは、管理者権限へ自動的に戻して実行せず、再読み込みを求める。
- 同じブラウザーのタブで切り替え状態を共有する。ログアウト時に解除し、元の管理者セッションが失効・変更された場合も継続できない。

## 実装と検証

1. サーバーの環境制限、署名Cookie、対象者解決を認証モジュールにまとめ、hookで実効ユーザーを設定する。
2. ユーザー選択画面と共通バナーに開始・終了操作、処理中表示、エラー表示を付ける。
3. 外部更新の停止をGitHub更新処理に適用し、稼働開始時の説明と再同期の拒否を明示する。
4. 環境制限、非管理者・未ログイン・Cookie改ざん・期限切れ・セッション変更、外部更新と並行処理の隔離を単体テストする。
5. 専用の一時DBで本人画面・管理者画面拒否・プロフィール編集・申請・管理者への復帰をE2E検証し、既存ローカルでは画面切り替えだけを確認する。スキーマやmigrationは変更しない。
